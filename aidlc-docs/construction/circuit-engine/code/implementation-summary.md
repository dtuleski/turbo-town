### Property tests (`fast-check`, `numRuns: 100`, `seed: 42`)

1. `evaluate` returns a typed outcome and never throws, for `fc.anything()` in all three
   arguments, and for well-formed layouts handed arbitrary switches and environments
2. determinism - identical input gives a deep-equal result
3. order independence - shuffling both input arrays gives **bitwise identical** per-element
   currents, asserted with `Object.is`
4. every `intensity` lies in `[0, 1]`; every current, voltage drop, node voltage, and total is
   finite
5. monotonicity - raising the source voltage never lowers any element's current magnitude
6. adding series resistance never raises the current through the chain

## 4. The three decisions this unit owned

### (a) Numeric bounds

`MAX_ELEMENT_COUNT = 64`, `MAX_CONNECTION_COUNT = 128`, grid `24 x 16` (min `2 x 2`),
`MAX_ID_LENGTH = 64`, source voltage `[1.5, 12]` in 0.5 V steps, light level `[0, 1]`,
resistance `[1, 10000]`, and the derived `MAX_MATRIX_DIMENSION = 256` from
`2 * 64 + 64 + 64`. Exported individually and as the frozen `CIRCUIT_LIMITS`.

Cost at the ceiling: about 5.6 million floating-point operations, single-digit milliseconds. A
realistic guided level sits near `n = 20`, about 2 700 operations - microseconds. Full rationale
per constant in `nfr-requirements.md` section 1.

### (b) Short-circuit threshold

`SHORT_CIRCUIT_RESISTANCE_THRESHOLD = 1.0` ohm, strict `<`, applied to **two** measurements:
the minimum-resistance passive path between a source's terminals with **every source excluded**,
and the external resistance a solved source is driving (`|terminal voltage| / |current|`).

A wire path is 0 ohm and trips; the smallest legal resistor is 1 ohm and does not; the smallest
fixed load is the LED at 30 ohm. Because `MIN_RESISTANCE` equals the threshold and the
comparison is strict, no single legally buildable resistance lands in an ambiguous zone.

Both measurements are needed, and the reason is the reachable multi-source case. A source edge
carries its internal resistance, so a passive search that excluded only the source under test
would route through a second battery for 0.5 ohm and report a short on two batteries wired in
parallel - a layout the solver simultaneously shows delivering a healthy 0.149 A. Excluding
every source fixes that but would then miss two batteries in series shorted by a wire, where no
passive route exists yet 18 A flows. The solved test covers that case, and clears the parallel
one at about 120 ohm per battery. Worked numbers in `functional-design.md` section 6.

### (c) Historical fault count clamp

`MAX_FAULT_COUNT_PER_LEVEL = 20`, with an optional per-level `maxFaultCount` override and
`clampFaultCount(reported, level)` returning `{ value, wasClamped, wasMalformed }`.

**Recommendation to U6**: reject the submission when `wasMalformed` is true rather than coercing
it, accept the clamped value when only `wasClamped` is true, and floor the total fault penalty
in E3 so a score can never go negative. The clamp bounds over-reporting only -
under-reporting stays unprovable in either direction, and no clamp changes that. See residual
risk below.

## 5. Deviations from the approved design, and why

| Change | Reason |
|---|---|
| `ElementResult` gains `kind` | Required, not optional: the approved `evaluateRoleActivation(machine, result)` receives no layout, so the result itself must say what kind each element is for B3 role binding |
| `resolveNodeIdentity(layout, mergePolicy)` instead of `(netlist)` | A closed switch is a conductor and an open one is a break, so the merge rule is switch-state dependent and a netlist carries no switch state |
| `resolveTopology(netlist, switches, env)` takes `env`; `buildConductanceMatrix(graph)` does not | Resolving each element's resistance and voltage once, in one place, avoids two sources of truth for the same number between A2 and A3 |
| `detectFaults(partial, graph, singular)` drops the separate `netlist` parameter | It is reachable as `graph.netlist`; passing it twice invites the two copies to disagree |
| `closedPathExists` derived from solved currents, not graph reachability | **Correctness fix.** See below. |
| `params.internalResistance` added, bounded to `[0, 10000]` | Lets content model a fresh cell against a worn one, and makes a pure ideal source expressible, which the bridge cross-check needs |
| `LevelDefinition.maxFaultCount` added as optional | Carrier for decision (c); optional, so no consumer breaks |
| Sandbox budget is 8 per kind, not 64 per kind | 8 kinds at 64 each would total 512, violating `MAX_ELEMENT_COUNT`. 8 each sums to exactly 64 |
| Buzzer 180 ohm (not 120), motor rated 0.22 A (not 0.20) | So that across the whole legal voltage range no single non-LED load alone on a battery overloads. At 120 ohm the buzzer would spuriously fault above about 9.6 V, and the motor's margin at 0.20 A was 0.8 percent. The unprotected LED stays the only overcurrent lesson |

### The `closedPathExists` correctness fix

The first implementation searched the conduction graph over the product of node and "has a load
been traversed". A test caught it: that search returns true for a battery shorted by a wire with
an LED hanging off a dead-end branch, because the walk can enter the LED and reverse back out,
traversing a load edge while carrying no current.

Carrying current **is** the FR-CB-10 condition, so it is now read off the solved currents:
`closedPathExists` is true when some load element carries current above `CURRENT_EPSILON`. This
is exact rather than approximate and also handles a second case the graph search got wrong - a
load in parallel with a dead short, where the short collapses the terminal voltage and the load
carries nothing. Both cases now have tests. `hasClosedPath` remains as A2's purely topological
predicate, which is exactly the responsibility the Application Design assigns it.

## 7. Residual risk

1. **The LED is a linear resistor, not a diode.** Reverse current still flows mathematically
   and is suppressed by the fault detector rather than by the model. A deliberate
   simplification: a real diode would block it. The visible consequence is that a reversed LED
   reports `REVERSED_POLARITY` with `energized: false` while its computed `current` is non-zero
   and negative. A consumer that reads `current` without checking `energized` would see current
   through a backwards LED. `OVERCURRENT` is suppressed in this case so the player does not get
   a second, misleading tooltip.

2. **`faultCount` remains unprovable downward.** The clamp bounds over-reporting only. A player
   who reports zero faults after causing five is indistinguishable from one who caused none.
   Closing this would require streaming fault events to the server during play, which is out of
   scope. Bounded and documented, not eliminated.

3. **Conductor current is not individually determined.** An ideal conductor reports
   `current: 0` and `voltageDrop: 0`, which are true under the model, with `energized` derived
   from whether its component carries source current. A UI that wanted to label a wire with an
   ammeter reading would need the engine to model wire resistance, which it deliberately does
   not.

4. **`totalCurrent` and `totalResistance` describe the dominant source only.** `summarize`
   picks the source carrying the largest current, ties broken by the smallest element id, so a
   circuit driven by two sources **understates** both totals. Two batteries on common rails
   feeding one motor report `totalCurrent = 0.0747 A` - one battery's share - rather than the
   0.1494 A the motor draws, and `totalResistance = 120 ohm` rather than the motor's 60 ohm.
   Per-element results are exact and unaffected. **U3 and U6 must not read these two fields as
   whole-circuit figures for a multi-source layout**; sum the source currents in `elements`
   instead. Single-source layouts, which every guided level is, are exact. Changing this would
   mean redefining both fields for a case the authored levels do not contain, so it is
   documented rather than changed.

5. **A stale `switchStates` entry invalidates the whole layout.** A key naming no existing
   switch element raises `UNKNOWN_SWITCH_ELEMENT`, and `evaluate` treats any structural issue
   as fatal, so a reducer that deletes a switch element without pruning its map entry gets
   `STRUCTURAL_INVALID` instead of a result. This is deliberate and now an explicit contract
   on C5 in `functional-design.md` section 2: delete the element and its entry in one state
   update. The strictness is what keeps the server from accepting a payload whose switch map
   and element list disagree (SECURITY-05); the returned issue names the offending
   `elementId`, so a drifted client can prune exactly that key. The alternative - silently
   ignoring unknown keys - was rejected because it would make browser and server accept inputs
   they cannot both account for.

6. **Only two levels are authored** - `cb-01-closed-circuit` and `sandbox`. FR-CB-27 asks for
   six to eight guided levels; the remaining content is unit U4's scope, and the level model
   and success-condition registry are in place to receive them.

7. **Test files are not type-lint-able in this package**, a pre-existing condition.
   `tsconfig.json` excludes `**/*.test.ts` while `npm run lint` globs all of `src`, so every
   test file - the two that already existed and the twelve added here - reports an ESLint
   parsing error. The package lint baseline was 12 errors and 13 warnings before this work
   (including `no-explicit-any` errors in `src/types/errors.ts`). New source files add **zero**
   errors and **zero** warnings. Test files are type-checked by `ts-jest` during `npm test`, so
   they are not unchecked - only unlinted. Fixing the lint configuration would mean editing
   `tsconfig.json` or `.eslintrc.js`, which is outside this unit's additive-only scope.

8. **`MAX_MATRIX_DIMENSION` is enforced by a throw**, converted to `INTERNAL_ERROR` by the
   facade. It is unreachable given that validation bounds the element count first, so it is
   defence in depth rather than a live path, and consequently has no direct test.

nothing in the design was redesigned to do it.

| 2 | **Blocking.** `evaluate` froze an object inside its input: `locateFaultPosition` returned `element.position` by reference and `freezeResult` froze it | `locateFaultPosition` returns a copy. | 4 | The published complexity budget covered Gaussian elimination only | `nfr-requirements.md` section 1 now budgets both passes - elimination at about 5.6 M operations, the short-circuit search at `64 * 128^2` = about 1.05 M, total about 6.7 M - with the conduction-graph node bound derived rather than asserted |
| 5 | The `fast-check` version claim in this document was inaccurate | Replaced with the table above, read from the manifests |
| 6 | Multi-source totals reported one source's view, explained only in a code comment | Residual risk 4 here, plus `functional-design.md` section 4 with the worked two-battery numbers and the instruction to sum source currents instead |

direction the finding asked for: two batteries wired in parallel to a load no longer pop the
fuse. Series-source shorts still report, with the spark now on the battery rather than on a
wire, because the other source is the rest of the loop and there is no passive element to blame.
